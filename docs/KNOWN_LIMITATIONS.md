# Known limitations (honest non-fixes)

- An owner who is socially engineered into typing an attacker's address is out of scope: AIRLOCK trusts the owner's own words.
- Labels are only as correct as the runtime code. The runtime is unattested (local mode) unless a TEE registration tx is linked in docs/EVIDENCE.md. Either way the contract's content limits (book, caps) still hold if it lies.
- Side channels acknowledged by CaMeL (timing, exceptions) are not closed.
- Host-delivered env vars (API keys) are visible to the TEE host. Live model calls go only to NEAR AI Cloud's TEE models (`TEE_MODELS` in `runtime/src/llm/models.ts`), but AIRLOCK does not check their enclave quotes per call, so the privacy of the owner's requests and the inbox text rests on NEAR AI's own checks; no security property depends on it, because the planner and the reader are treated as untrusted, and each recording names the route that made it.
- Approval fatigue: escalations are rate-limited and batched, but a determined attacker can still generate approval requests. The only auto-executions an attacker can influence are amounts read from data to an address-book payee inside that payee's cap, its daily untrusted budget and the task bound (the K2 envelope; strict mode removes it).
- A local task key authorizes unattended spending up to the quick cap.
- The console is in the trusted computing base.
- Tools are fixtures (no real connectors); testnet only. Because the fetchers are fixtures, no network call or file read happens in a tool, so the SSRF and path-traversal checks a real connector would need do not exist yet; names are map keys, never paths.
- No cancel (an issued but unbroadcast signature blocks later nonces for that path; use set_nonce or a new path); no owner transfer.
- A signing or transfer callback that runs out of gas leaves its request `Executing` and charged: no owner method clears it in this version, and the task ledger never resets, so that request's amount stays counted against its task. The lane reserves the callback's gas and AIR-107 measures the real burn on both the success and the refund path.
- An answer the contract cannot read after the signer's receipt succeeded (it does not parse, it is too long, or an EVM recovery id is above 1) keeps the request charged and `Failed`, because the signature may still be usable; the owner sees it in the `failed` event (`MpcBadResponse`, `retryable` false). Only a failed signer receipt, a failed transfer and an uncovered payment release the charges.
- Lean covers semantic models of the gate and the interpreter, not the shipped TypeScript (the TypeScript interpreter is covered by a property test).
- The noninterference model in `proofs/NI.lean` and `proofs/NI_recipients.lean` differs from `runtime/src/interpreter/interpreter.ts` in these ways (the theorem statements are unchanged and the proofs add no axiom):
  - Values are natural numbers with a taint bit. The interpreter handles JSON values and decimal strings, and `calc` is modelled as an arbitrary total binary function.
  - The model has no `say`, no `call` with arguments and no `extract` input. A tool result is an untrusted or oracle read that does not depend on the store, while the interpreter joins the labels of the call's arguments and the pc into the result, which can only add taint.
  - A run that aborts (a bad number, a bad condition, a refused tool argument, an unknown asset) has no result in the model, and the theorem covers pairs of runs that both complete. The interpreter aborts the whole run, so no proposed action of an aborted run is returned, but the abort itself can depend on untrusted data and is a timing or exception channel, as stated above.
  - Branch conditions are numbers (non-zero is true). The interpreter requires a boolean read and aborts otherwise. Loops run over a bounded count whose index carries the count's taint, while the interpreter iterates over the first `max` elements of a list and gives each element the list's labels.
  - Literal grounding (AIR-127) is a static choice per literal (`lit` or `ulit`). In the interpreter it is a function of the literal and the owner's text, so it agrees between two worlds that share the owner's text, which the theorem assumes.
  - Single assignment is checked at run time in the model (a re-binding aborts). The interpreter relies on rule 12 (`checkPlan`) before the run and binds names in per-branch and per-iteration scopes. The model has no assets: rule 12 forbids a data-derived asset argument and the interpreter takes the asset from the action name or the static chain id.
  - A read-only run (D21) proposes no action, so the theorem holds for it trivially. The model does not contain it.
  - The model's actions are proposals. The contract's verdict (`proofs/Verdict.lean`) decides whether a proposal pays.
- Future work, not attempted: extracting the Lean model from the Rust verdict crate with Aeneas (AeneasVerif/aeneas) so that the code-to-model link is itself a proof. Today the link is the differential test and Kani on the shipped Rust. The Aeneas Lean backend pins Lean v4.35.0 like we do, but it needs Mathlib, a recent OCaml and a pinned Charon, which this build does not carry.
- Payment before delivery: an x402 or MPP server that takes the payment and never delivers is out of scope, because AIRLOCK checks where a value came from and how much moves, not whether the seller keeps its side.
- The availability channel is open: an attacker can cause escalations, so approval requests can pile up. The pending cap, the hourly escalation budget and the lock on an agent bound how many reach the owner; they do not stop the owner from being asked. AIRLOCK does not claim there is no side channel.
- Literal grounding checks that a value occurs in the owner's words, not its pairing: a literal grounded in the owner's text can still be put against the wrong payee. The contract's book, payee caps and task bound still apply to that payment.
- Live x402 settlement is shown once, on testnet only: one 0.01 test USDC payment on Base Sepolia, signed by the MPC through the policy contract and settled by the public testnet facilitator (tx 0x631d4a3f...2025, docs/EVIDENCE.md). It is not a mainnet claim, and one earlier attempt failed at the facilitator's own broadcast and expired unsettled.
- No console page adds payees, so the look-alike check at `book_add` exists only as a pure function (`checkBookAdd` in `runtime/src/dsl/lookalike.ts`); the approvals card still warns on a look-alike of a book payee when the owner is asked.
- The task key needs WebCrypto Ed25519 in the browser. A browser without it gets `KeyUnsupported` and the console refuses to sign.
- There is no reject-all by design: three consecutive rejects lock an agent's escalations (`lock_consecutive_rejects`), which stops a flood but does not clear the pending requests.
- A careless owner can approve a truthfully displayed bad payment: the console shows the real payee and amount, and the contract rechecks the approve arguments, but it cannot stop an owner who does not read the card.
- The bench volume numbers come from a simulated world fed by the verdict CLI, and benign utility is in-sample. The contract-level evidence is the sandbox suite; see docs/BENCH.md.
- The look-alike twin payee in the bench was never actually fallen for in the three live runs of 2026-11-04 recorded in docs/EVIDENCE.md, so there is no live twin-loss claim: no golden run shows the vanilla or the allowlist twin losing money, and none is claimed.
- Runs are on testnet only; no mainnet transaction was made and no mainnet claim is made.
- The replay demo needs no keys and no network; it replays recorded model answers and chain reads, so it shows the recorded runs and is not a live run.
- The model attestation (AIR-303) covers the model TEE instance that answered one report request with our nonce. NEAR AI Cloud says the same hostname can be served by several instances that share one signing key, so the report does not name the instance that answers a later completion, and no per-completion response signature is checked. The GPU verdict is NVIDIA NRAS over TLS, with no local check of its token. Quote collateral comes from Phala's PCCS and is checked against Intel's root key. A replay shows the stored result of one live check and does not repeat it. A runtime started live without a key, or with a failed check, serves an UNATTESTED or FAILED record and keeps running.
- NEAR AI may serve more than one model build behind the same name (one run on 2026-11-03 saw an unpinned compose hash; ten later samples showed one build). Only pinned builds verify: an unpinned build is reported FAILED, with the seen hashes in the record, and is never trusted. Adding a build is the manual, reviewed `attest-rotate` step.
- Local mode is unattested; host powers (a host can stop, delay or read the runtime) are not removed by any check here; oracle dust moves; plan_hash and evidence are unauthenticated hints; UTC-boundary burst.
- Wallet manifest pinning fixes which wallets the console offers, not the wallets' code: a wallet executor such as Intear's is a
  remote script that can change; the contract's recheck of the five approve arguments after the request id is the control.
- The console CSP allows inline styles and lists a per-wallet executor origin, because NEAR Connect 0.11.4 injects styles and loads wallet scripts from remote origins; scripts stay `'self'` plus a per-response nonce.
- The runtime's evidence store is in memory and is lost when the runtime restarts.
- The session cookie is `Secure`, so a demo over plain `http://<LAN address>` cannot log in; use localhost or HTTPS.
- near-api-js `FailoverRpcProvider` is not used; the runtime has a sequential `RpcPool` instead, so its failover behaviour is our own code.
- Sandbox gas numbers come from neard 2.11.0 (protocol 83); testnet runs protocol 88, so published gas figures are the testnet
  measurements of AIR-107.
- Evidence injection: fabricated facts that steer a decision inside the owner's limits (for example a fake price or
  news item that makes a legitimate payee's in-cap payment look due) are out of scope; AIRLOCK bounds where values come
  from and how much can move, not whether a trusted-looking fact is true (arXiv 2610.26438).
- Untrusted text never enters planner memory; carryover memory attacks (arXiv 2610.28425) are blocked only because
  memory is always labelled untrusted.

- Adaptive round (AIR-231, docs/BENCH.md "Adaptive round"): hand-written attacks played with a fully hijacked reader found no value past the envelope the owner set, and three things the earlier text did not say. (1) The envelope is a daily figure: an owner who keeps running tasks that pay an address-book payee from data lets an attacker auto-execute the payee's untrusted budget every UTC day (10 NEAR a day in the bench book, 30 NEAR over three simulated days), in steps no larger than the cap, across any number of tasks, and an amount equal to the cap passes. Strict mode removes it. (2) The look-alike heuristic and the counterparty note are hints and miss cheap cases: a name three or more edits from a book name (digit-for-letter swaps, a plausible prefix or suffix, another top-level account), a NEAR account created a week ahead of the attack, and an EVM address the attacker funded with one wei all show no warning on the approval card. The contract still escalates every such payee, so the owner is asked, but the card does not help. (3) The expected asset of `fetch_paid` is a plan's own choice: it is `near` unless the plan names another with `expect_asset`, so the tool cannot tell whether a plan that names `expect_asset` then pays in that asset; the planner is trusted for that pairing.
- Fixed after the adaptive round (commit e21e6b6): the Intents quote check accepted an echoed request that carried an extra `appFees` recipient, and `fetch_paid` handed the plan an amount priced in another asset (ADP11), so 4.9 of a foreign token was paid as 4.9 NEAR. Now `checkQuote` refuses any fee recipient not on `allowedFees` (`UnexpectedFee`) and any key of the echoed request that was neither sent nor a known server default, and `fetch_paid` refuses a requirement whose asset is not exactly the expected one (default `near`, or the plan's `expect_asset`; `X402AssetMismatch`, a `ToolError` abort), on every network (follow-up commit after e21e6b6).

## Upstream code we own
The contract's agent registration and verification code derives from NEAR's Shade Agent template (commit 816b75b) and the
`shade-attestation` 0.2.0 crate. NEAR stopped maintaining the Shade Agent Framework as standalone developer tooling
in April 2026, and its repositories state it has not had a formal audit. We pin both, own the fork, and track
upstream security fixes ourselves.

- Literal grounding (defense in depth, never the wall) compares ASCII only: a non-ASCII character joins the word it touches, so a look-alike name or address never grounds, but digits are matched as ASCII runs, so owner text mixing scripts inside a number (`1٠25`) can ground the ASCII part (`25`). Such a literal is still checked against the book, the payee caps and the task bound.
- Host-header DNS rebinding (AIR-167): the runtime server binds the configured host (loopback by default) but does not check the `Host` header. The `Origin` check compares `Origin` with `Host`, so a page on a rebound attacker name passes it. That page can request a challenge and read it, but it has no owner key to sign it and the `SameSite=Strict` session cookie belongs to the console's own name, so no session results. A Host allowlist is out of this pass; test: `runtime/test/session.test.ts` Origin test shows the same-host rule.
- A non-GET request with no `Origin` header is accepted by the `Origin` check (AIR-167): browsers always send `Origin` on a cross-site POST, and the cookie is `SameSite=Strict` with no CORS headers, so only a non-browser client omits it, and that client holds no cookie it did not obtain by logging in.
- The 200 byte Ledger claim for the arguments of `approve` covers `near` and native EVM assets only (AIR-109): the payee key of an erc20 asset is up to 112 characters, the worst case of the demo asset is 208 bytes and a typical escalated x402 approve is 191 bytes, so the AIR-086 guard is skipped for erc20 assets.
- x402 retries re-sign the one stored authorization (AIR-109): a retry never takes a new nonce or window, because the first signing may have completed in the signer even when the callback saw a failure. Once the stored `valid_before` has passed, the retry signs nothing; it reverts until NEAR block time is at or past `valid_before` plus a 300 s skew margin, then the request fails with `AuthorizationExpired` (charges released) and the agent must send a new request. The margin keeps a NEAR clock ahead of Base from releasing the charges while the old authorization is still redeemable.
- The counterparty note (AIR-304) is a runtime hint stored with the evidence, not an input of the verdict: the contract does not see it and nothing authenticates it. "New" means a NEAR account that did not exist about 7 days ago (by block count at one second per block, read from the archival RPC) or an EVM address with no nonce, balance or code; a payee in the book is never looked up. A failed lookup shows as unchecked, and a payee outside the book already never passes the gate.
- The NEAR Intents 1Click quote leg (AIR-305, docs/INTENTS.md) is dry only: Intents has no testnet, a dry quote carries no deposit address, the quote's own signature is not verified, and a pass signs nothing.
